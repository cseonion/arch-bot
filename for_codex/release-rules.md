# 버전 및 릴리스 규칙

## 기본 원칙

- 모든 기능, 수정과 운영 변경은 즉시 `CHANGELOG.md`의 `[미출시]`에 누적한다.
- 커밋마다 버전을 올리지 않는다.
- 서로 연관된 변경이 하나의 배포 가능한 사용자 가치로 완결된 뒤 버전을 올린다.
- Draft PR이나 기능 브랜치에서는 tag와 GitHub Release를 만들지 않는다.
- `main` 병합, 깨끗한 작업 트리와 CI 성공을 확인한 뒤 Release를 발행한다.

## Semantic Versioning

- MAJOR: 기존 사용법이나 운영 계약을 깨는 변경
- MINOR: 호환성을 유지하는 새 채널, 파일 형식, Tool 또는 주요 기능
- PATCH: 버그, 보안, 문서와 운영 보정
- 긴급 보안 문제나 치명적 장애 수정은 누적량과 관계없이 PATCH 후보로 삼는다.
- 운영 안정성과 지원 범위가 확정되기 전에는 `v0.x.y`를 사용하고 `v1.0.0`
  발행을 보류한다.

## 변경 묶음 기준

다음 중 하나를 만족하면 릴리스 후보로 검토한다.

- 사용자가 바로 사용할 수 있는 하나의 완결된 기능 묶음
- 서로 관련된 사용자 기능 또는 수정이 3개 이상 누적
- 긴급 보안 또는 운영 장애 수정

`pyproject.toml` 버전, 애플리케이션 버전, `CHANGELOG.md` 버전 섹션, Git tag
`vX.Y.Z`, GitHub Release 버전을 일치시킨다.

태그를 Push하면 `.github/workflows/release.yml`이 CHANGELOG의 해당 버전 두 단을
검증하고 GitHub Release를 자동 생성한다. 태그 전 반드시 CHANGELOG 버전 섹션과
애플리케이션 버전을 먼저 커밋한다.

## 한국어 Release 형식

```markdown
# vX.Y.Z — 릴리스 제목

## 1. 서비스 사용자용 변경 사항

- 사용자가 무엇을 새로 할 수 있는지 쉽게 설명

## 2. 개발자용 업데이트 로그

- 구현 모듈, 설정, 데이터 흐름, 호환성 및 검증 내역
```

릴리스할 때 `[미출시]` 항목을 날짜가 있는 버전 섹션으로 옮기고 빈 `[미출시]`
두 단을 다시 만든다.
